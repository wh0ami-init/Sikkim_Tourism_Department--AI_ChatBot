01 · Project Overview

A trusted digital guide for Sikkim visitors.

The Sikkim Tourism Assistant is a web application for destinations, permits, routes, travel advisories, registered travel agencies, and practical itinerary assistance. It is designed to prioritise Department-managed records over generic AI answers.

04 · Database Design

MySQL schema and entity relationship model.

The production application uses MySQL as the authoritative operational database. Qdrant stores retrieval vectors and does not replace the structured source-of-truth tables.

destinations

  • PK id
  • name, slug, category
  • district, description
  • permit_required, permit_info
  • latitude, longitude

circulars

  • PK id
  • title, category, district
  • issue_date, source_url
  • pdf_hash UNIQUE
  • extracted_text, ingested_at

conversations

  • PK id (UUID)
  • created_at

messages

  • PK id (UUID)
  • FK conversation_id
  • role, content
  • client_message_id
  • created_at

admin_users

  • PK id
  • username UNIQUE
  • password_hash
  • created_at, updated_at

travel_agencies

  • PK id
  • name, district
  • registration_number UNIQUE
  • contact, address
  • synced_at

Table Purpose Integrity / Indexing
destinations Department-managed visitor catalogue. Unique slug; full-text name/description search; category constraints.
conversations → messages Anonymous visitor chat history. UUID identifiers; foreign key with cascade; idempotency unique key on conversation/message ID.
circulars Official notices, road reports and cancellation orders. SHA-256 uniqueness prevents duplicate ingestion; category/date index supports freshness queries.
travel_agencies Approved directory records. Unique registration number; district and full-text indexes.
admin_users Protected Department accounts. Unique username; salted password hashes only—never plaintext passwords.

05 · Security by Design

Protection is built into the application boundary.

Authentication & access

  • Bootstrap setup requires a server-side secret.
  • Admin actions require valid credentials and rate limiting.
  • Passwords use salted scrypt hashes.
  • Credentials are never placed in browser local storage.

Input & upload safety

  • Request values have constrained types, lengths and formats.
  • Images and circular uploads are size-limited and signature-validated.
  • Client-provided MIME types are not trusted by themselves.
  • Destination image URLs are limited to local approved paths.

Browser & API controls

  • Explicit HTTPS CORS origins in production; wildcard is rejected.
  • CSP, anti-framing, no-sniff, referrer and permissions headers are applied.
  • Conversation and admin responses are non-cacheable.
  • Public advisory projection omits internal OCR and ingestion metadata.

AI safety & integrity

  • Retrieved text is treated as reference material, never as executable instruction.
  • Road status and agency data are answered from verified records.
  • Issue dates communicate the freshness of official advisories.
  • Unknown official facts are reported honestly rather than guessed.

07 · Deployment & Operations

Controlled deployment requirements.

Production prerequisites

  • HTTPS frontend and backend domains.
  • Managed MySQL with TLS and tested backups.
  • Hosting-platform secret manager for all keys.
  • Reverse proxy/WAF with a request-body limit.
  • Restricted outbound access for optional scraper operation.

Operational ownership

The Department should assign owners for destination data, circular review, agency-directory synchronisation, admin access, backups, incident response, and periodic dependency review.

Important: API keys, passwords, bootstrap secrets and database connection strings must never appear in documentation, source control, screenshots or email.

08 · Acceptance Criteria

Conditions for Department-controlled release.

  1. Department approves content, data governance, branding and hosting arrangements.
  2. Production HTTPS, explicit CORS origins, secrets and MySQL TLS are configured.
  3. The schema and required migrations have been reviewed, backed up and applied.
  4. A Department administrator successfully completes secure setup and authenticated operations.
  5. Public destination, chat, advisory and agency workflows pass acceptance tests.
  6. Current backend tests, frontend build, and dependency security checks pass for the release candidate.
  7. Backup, restoration, monitoring and incident contacts are documented by the operating team.
